# Decision Log — Storage Engine, event_log Table, and Alembic Migrations

**Date:** 2026-07-21
**Area:** storage

## Context

The session started from a pasted setup snippet for a Next.js app (`npm install @supabase/supabase-js @supabase/ssr`, `utils/supabase/{server,client,middleware}.ts`, a `page.tsx` server component). That doesn't apply to this repo: Project Atlas is Python-only (no `package.json`, no Next.js app), still in Phase 0 with no frontend until Phase 1, and `docs/architecture/Phase0_Architecture.md` already specifies Supabase is reached via SQLAlchemy 2.0 + Alembic, not the JS client. The mismatch was flagged and the user confirmed the actual intent: stand up real Supabase/Postgres access in the way this project's stack already calls for. This was also the literal next item in `docs/tracker.md`'s "Next up" list (`storage/db.py` + `storage/tables.py`, following the schema/storage line item).

## Decisions

1. **Scope this pass to connection + table + migrations only, not projections.** `storage/projections.py` (event replay → materialized Node/Edge views) needs the Pydantic `Node`/`Edge` schema (`models/schema.py`), which is still an empty stub and a separate tracker item. Bundling projections into this pass would have meant designing replay logic without the types it replays into — deferred instead of half-built.
2. **`event_log` table matches TRD §3.1's `Event` shape exactly**: `id` (UUID), `event_type` (enum matching the seven TRD-listed values), `payload` (JSON), `actor` (text), `timestamp`, `workspace_id` (UUID). Read from the TRD rather than re-derived from memory, per CLAUDE.md's documentation discipline.
3. **`payload` is a generic `JSON` type with a `.with_variant(JSONB(), "postgresql")`**, not a bare `postgresql.JSONB()`, so tests can run against in-memory SQLite (no live Supabase project exists yet) while production still gets real JSONB on Postgres.
4. **The `EventType` enum column needs `values_callable`** so SQLAlchemy persists the lowercase TRD string values (`"node_created"`) rather than defaulting to the Python enum's uppercase member names (`"NODE_CREATED"`) — the latter would silently mismatch the Postgres-side enum type the migration creates and break every write. Caught via the `backend-reviewer` agent's review pass.
5. **Append-only is enforced by convention only in Phase 0**: no `update_event`/`delete_event` function exists anywhere in `storage/`, and a test asserts as much. There is no DB-level guard (grant/revoke or a blocking trigger) yet — flagged as a deferred decision, not resolved this session (see Not done).
6. **The first Alembic migration is hand-written, not autogenerated.** Autogenerate needs a live DB connection to diff against, and no Supabase project had been provisioned at the point the migration was first drafted. The migration mirrors `EventLog` column-for-column by hand, with an explicit note in the file explaining why. It needed a `create_type=False` on the column-level enum definition (with a separate explicit `.create()`/`.drop()` call for the type itself) to avoid Alembic trying to create the same Postgres enum type twice — a real bug, caught when the migration was run against the live Supabase instance (it fails silently in offline/`--sql` mode since that never actually executes the DDL).
7. **`psycopg[binary]>=3` added as a dependency**, and `normalize_database_url()` rewrites bare `postgresql://` connection strings (the shape Supabase hands out) to `postgresql+psycopg://`, since SQLAlchemy's default dialect for the bare scheme is psycopg2, which isn't installed.
8. **The DB URL is never committed anywhere.** `alembic.ini`'s `sqlalchemy.url` is left blank with an explanatory comment; `migrations/env.py` reads `SUPABASE_DB_URL` from the environment at runtime instead, matching CLAUDE.md's "no secret ever lands anywhere but env/secrets manager."
9. **Built test-first per the `tdd` skill**, since this is event-log/storage logic (mandatory test-first per CLAUDE.md). Tests run against in-memory SQLite, not live Postgres, so they run in CI with no secrets — table shape, write/read round-trip, transactional rollback, the enum-value-vs-name regression, and the URL-normalization behavior are all covered there. The Postgres-only DDL (JSONB, the native enum type, the `id` server-side default) was additionally verified against the real Supabase instance directly (migration applied, table inspected, a real row written/read/deleted), since SQLite's leniency (no native enum constraint) had already been shown to mask at least one real bug.
10. **`id` has a DB-level default (`gen_random_uuid()`) in addition to the ORM-level `default=uuid.uuid4`.** Without it, an insert that bypasses the ORM (a raw SQL script, a manual console insert) would hit a NOT NULL violation — caught via `backend-reviewer`.

## Not done (deferred)

- **DB-level append-only enforcement** (REVOKE UPDATE/DELETE, or a blocking trigger on `event_log`) is not implemented — Phase 0 currently relies on `append_event()` being the only exposed write path. Worth revisiting before more code paths get a raw `Session` handle.
- **`models/schema.py` (Pydantic Node/Edge/SourceRef/Event) and `storage/projections.py`** remain empty stubs, deliberately out of scope for this pass (see Context).
- **`EventLog.workspace_id` is `nullable=False`** (matching TRD §3.1 exactly), but Phase 0 has no workspace-creation flow and CLAUDE.md defers multi-tenancy/RBAC to a later phase. Something needs to answer "what workspace_id do I pass?" before `ingestion/github.py` or `extraction/agent.py` can call `append_event()` — flagged by `backend-reviewer`, not resolved this session.
