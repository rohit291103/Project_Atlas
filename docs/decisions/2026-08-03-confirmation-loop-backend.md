# Decision Log — Confirmation-Loop Backend (Phase 1, Slice 1A)

**Date:** 2026-08-03
**Area:** storage, models

## Context

Phase 1 slice 1A (`docs/architecture/Phase1_Architecture.md` §3, §4) makes the extraction loop *writable*: the confirm/edit/reject/add actions of TRD §6, which Phase 0 deliberately left unbuilt. Three forward notes came due at once — the status-transition replay handlers (`docs/decisions/2026-07-22-projections-event-replay.md`), the monotonic sequence column, and `Node.confidence_score` becoming optional. Built test-first per the `tdd` skill (projection replay and schema validation are both in its mandatory-discipline set).

## Decisions

### 1. `event_log.sequence` — a database-assigned append order

Added `sequence BIGINT GENERATED BY DEFAULT AS IDENTITY`, unique, with a composite `(workspace_id, sequence)` index serving the replay query. `load_projection` now orders by it instead of `(timestamp, id)`.

Wall-clock `timestamp` was never a safe total order and becomes actively wrong once transitions exist: two events appended in one transaction can share a Postgres `now()`, and a clock adjustment can invert two of them — either of which can silently apply a confirm *after* the edit that superseded it. The migration backfills existing rows in `(timestamp, id)` order, the exact order the old code used, so replaying a pre-existing log yields the same projection before and after.

`sequence` is a storage concern only — it is deliberately **not** on the domain `Event` model (TRD §3.1 has no such field), because nothing in extraction or the future API reasons about it.

### 2. `confidence_score` is present exactly when the system extracted the node

`Node.confidence_score` is now `float | None`, with a model validator enforcing **both** directions: required when `created_by = system`, forbidden when `created_by = user`.

TRD §6 only asked for the first half ("manually-added nodes skip confidence scoring"). Enforcing the second half too keeps the field meaning one thing — how confident the *extractor* was — rather than quietly becoming "how sure the human felt" on some rows. Making it merely optional would also have let an extraction agent that omits the score be stored as unscored rather than rejected at the gate. Editing a node doesn't change `created_by`, so an edited node keeps the score its extraction earned.

`cli.py` renders an absent score as `—`, not `0.00`, which would read as "scored, and worthless."

### 3. Transitions supersede a node through the same validation gate

`replay()` handles `node_confirmed`/`node_rejected`/`node_edited` by rebuilding the node through `Node.model_validate` with the change applied plus `updated_by`/`updated_at` taken from the Event's own `actor`/`timestamp`. Not `model_copy`, not mutation: an edit passes the same gate a create does, so no transition can produce a node the schema would have refused (e.g. one with blanked content). The `_ReplayableEvent` protocol gained `actor`/`timestamp` rather than duplicating them into the payload, where the two could disagree.

A transition naming a node the log never created **raises**, matching the fail-loud posture of the Phase 0 decision it replaces: that combination means a corrupt log or an upstream bug, and swallowing it would make a confirm silently vanish.

Order is last-write-wins, so undo falls out for free (TRD §3.1) — a reject followed by a confirm leaves the node confirmed.

### 4. No `node_added` event type — manual add is `node_created` with `created_by = user`

`Phase1_Architecture.md` §4.1 proposed a fourth handler, `node_added`. Rejected: TRD §3.1's `event_type` enum has no such member, so adding one means a Postgres enum migration and a divergence from the data model of record, in exchange for nothing — a manual node is fully described by `node_created` with `created_by = user`, no confidence score, and `status = confirmed`. The existing handler covers it unchanged.

### 5. `storage/confirmations.py` — the write side, taking a `Node`, not an id

The four actions live in a new module inside the existing `storage/` boundary (the `codebase-design` gate applies to the proposed `api/` module and frontend, not to this). They are plain functions over a `Session`, so Phase 1's API and the CLI share one write path and payload shapes live in one place.

Each takes the `Node` it acts on rather than a bare id. That forces the caller to have loaded the projection — an action can't name a node that doesn't exist — and `workspace_id` comes off the node instead of being passed alongside, where the two could disagree.

`edit_node` reads `previous_content` off the node rather than accepting it as an argument, so the recorded before-image is always what was actually current.

`add_node` refuses a `created_by = system` node: routing extraction output through the manual path would launder a draft into a confirmed fact without a human ever seeing it.

### 6. `NodeEditPayload.previous_content`, not `original_content`

TRD §6 requires an edited node to "retain a link to the original system-extracted version." Implemented as the value the edit *replaced*, chained: walking `node_edited` payloads back to the `node_created` that started them recovers the original. Storing the system original on every edit was rejected because an edit-of-an-edit would then record a before-image that was never current at that point — a chain of true statements beats a repeated approximate one, and the name says which it is.

### 7. `append_event` rejects a blank actor

Every Event is the audit record of who did what (TRD §9). `Event.actor` in `models/schema.py` already forbade blanks, but the write path never constructs an `Event` — it writes the column directly, and `NOT NULL` doesn't catch `""`. Closed at `append_event`, the single sanctioned write path, so it holds for every writer rather than just the confirmation helpers.

## Open question raised here — since resolved

**Do manually-added nodes need a `SourceRef`?** `Phase1_Architecture.md` §8 assumed not; the `Node` schema, following CLAUDE.md's zero-exceptions rule, requires at least one. This slice kept the schema rule rather than relaxing the project's one non-negotiable invariant as a side effect of backend plumbing.

**Resolved the same day** — see `2026-08-03-manual-node-provenance.md`. Neither relaxing the rule nor demanding an external citation was right; `SourceType.human_assertion` keeps the invariant literally true while satisfying PRD R10. That decision also changed `add_node`'s signature (it now builds the Node from fields rather than accepting one), which supersedes the forward note below by making both risks structurally unreachable.

## Forward note (slice 1B/1D)

All four helpers take `actor` as an argument, and `add_node` takes `workspace_id`. The API must derive both from the authenticated session, never from a request body, or a caller could write into any workspace or forge an attribution. Nothing is exploitable today — there is no API and the CLI has no write command — but enforcement (workspace RBAC + RLS) is slice 1D, so until then it is a convention, recorded here so it isn't discovered by accident.

(As originally written this note also covered `add_node` accepting a caller-built `Node` with its own `workspace_id`/`feature_scope_id`; the signature change above removed that seam entirely.)

## Test coverage added

`tests/test_confirmations.py` (new, round-trip: write the event, replay the log, assert the projected node — the only assertion that proves the write and read sides agree on a payload shape), plus confirmation-transition, ordering, and `confidence_score` cases in `tests/test_projections.py`, `tests/test_storage.py`, `tests/test_schema.py`, `tests/test_cli.py`. `tests/conftest.py` is new and holds one thing: a SQLite shim assigning `sequence`, since SQLite cannot auto-generate a non-primary-key integer. It lives in the test harness, not in `append_event`, so the production write path carries no dialect branch — the same class of fix as the dialect-portable `_UUID` variant.
