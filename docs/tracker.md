## Engineering

### Done

- **Phase 0 complete** — `ingestion/` (read-only GitHub), `extraction/` (Claude Agent SDK + validation gate), `storage/` (event log + projection replay), `cli/`. Exit criterion met.
- **The four Phase 1 slices** — confirmation loop (1A), feature-scope identity (1A′), the React+FastAPI confirmation UI (1B), Jira as a second source with cross-source conflict detection (1C), scoped ingestion + workspace RBAC + tool-call audit (1D). Each verified live; details in the decision logs above rather than re-listed here.
- **Slice 2A — the product layer and the review rebuild.** `product` is a projection from three event types (it could not be derived from `external_id`: a product must exist *before* the first connection to it). An explicit assignment beats a run's default, in either order. Four zones replace the everything-at-once page; provenance has its own always-visible column; nine `NodeType` headers became four groups; conflicts are objects showing both sides; every screen has a real URL; confirm auto-advances.
- **Slice 2B — sources and ingestion from the UI.** The slice that makes "connect two sources" literally true:
  - **`storage/connections.py`** — the `connection` table, its CRUD, and Fernet encryption at the boundary. `ConnectionView` **has no field a secret could occupy**, asserted directly *and* over the generated OpenAPI schema the frontend's types are built from. Revocation is a real delete; the audit event survives it. Migration `a5d2f7c04e19` carries the table, its RLS policy, and the narrowest grants — written in the same revision, per `script.py.mako`'s header.
  - **The run lifecycle.** `ingestion_run_started` / `ingestion_run_finished` / `ingestion_run_failed` bracket the existing `ingestion_run`, whose meaning is unchanged (one artifact pulled). A run's state is **derived by replay, never stored** — and a start older than `INTERRUPTED_AFTER` (30 min) with no terminal event reports as **interrupted**, which is the honest cost of running in-process with no queue.
  - **`src/atlas/pipeline.py`** — parse a target → build a read-only client → run the agent → write validated events. Two real callers (`cli.py`, the ingest endpoint); `cli.py` now holds no orchestration and a test fails if it regains any. Credentials are *arguments*; nothing in `pipeline/` or `ingestion/` knows whether one came from `.env` or a decrypted row.
  - **The API's two new endpoints**, both keeping the thinness rule. `POST /products/{id}/connections` **verifies the credential against its scope and reports what it reaches** before storing it. `POST /products/{id}/runs` returns **202** and works in a `BackgroundTasks` — no broker, no worker, no new deployable.
  - **Cross-source conflicts work in both directions.** `extract_from_pull_request` gained `known_nodes`, mirroring the Jira path; without it a PM who connected Jira *then* GitHub would have silently received no conflicts at all. The Phase 0 seed prompt is byte-identical when nothing is offered.
  - **`scripts/verify_rls.py` extended to 17 checks, 17/17 live** — four of them on `connection`. The update/delete checks assert *"reached nothing"* rather than *"was refused"*, because that table legitimately holds all four grants and the policy filters rather than raising.
- **The post-login experience — product as context, and work-left everywhere.**
  - **The rail scopes to one product**, behind a `ProductSwitcher`. It previously showed every product's features interleaved in one flat column, which is the "Google Meet next to Google Keep" problem shipped. In-product nav (Overview · Conflicts · Sources) sits above the feature list; **Conflicts had no link anywhere in the UI before this** and was reachable only by URL.

A remembered id is re-checked against the products that came back, so a deleted one degrades to the chooser. **Only a fresh sign-in forwards** — `/app` is never hijacked, or "All products" would be unreachable.

One datum feeds the rail badges, the live `Conflicts (n)` nav entry and the product worklist; the alternative was shipping every claim of every feature to the browser to count them, with "unreviewed" defined three times. Conflicts count **disagreements, not claims-in-a-disagreement**, and both endpoints must be inside the scope — so a badge always matches the screen it opens. Rejected claims drop out.

## Last session notes

**The post-login screen was an inventory; it is now a worklist.** It answered "what products exist" — which the PM already knows — and answered it twice, because the rail listed every product *and* every feature. ~85% of the viewport was empty and nothing said what needed judgement. Three steps fixed it, taken deliberately one at a time.

**The shaping question came from the user and killed the first proposal.** A PM owning **Google Meet and Google Keep** is doing two different jobs — different repos, different Jira sites, different teams. A flat cross-product worklist would have put a Meet conflict next to a Keep conflict and forced a re-orientation on every row. So a product became a *context you are inside*: the rail scopes to one, a switcher changes it, sign-in reopens the last one, and "All products" stays reachable because a helpful default that cannot be escaped is a cage. This was already the product model's own claim — `ProductsPage` says "nothing crosses between them" — and the rail had been contradicting it.

**One backend change fed three surfaces, which is why it went in the projection.** `ScopeCounts` computes total/unreviewed/conflicts in `storage/projections.py`; the rail badge, the live `Conflicts (n)` and the new "Needs your ruling" list all read it. This amends `routes.py`'s "no counting endpoints" rule on a narrower line than it read: *how many are unreviewed* is a fact about stored state; *how to group and order them* is a screen decision and stays in the frontend. Conflicts count disagreements rather than claims-in-a-disagreement, so a badge always matches the screen it opens — and the review footer, which said "8 in conflict" while the rail said "6 conflicts", now names both.

**The typography complaint turned out to be drift, not taste.** `design-system-baseline-v1.md` §4 already specified `12/13/15/18/24` and "500 labels/tags". The build shipped a full step smaller at every level and, worse, **42 of ~90 `font-size` declarations bypassed the scale entirely to hardcode 10px**. Three colour tokens were failing WCAG AA at 3.06–3.85:1, and `--text-faint` was the one used *at 10px*. All corrected, colours re-solved rather than eyeballed, and a test now asserts computed sizes so the next 10px hardcode fails in CI — because a written scale is a suggestion until something breaks when the build disagrees with it.

**The landing page was rebuilt around live-DOM demos**, since the previous version argued entirely in prose and read as a manifesto for something unbuilt. Then the real app caught the demo **lying about its own keyboard shortcuts** — it advertised ⏎/E/R/A against the app's actual `c`/`e`/`x`/`a`. Exactly the drift the DOM approach was supposed to prevent, wrong on day one, which argues for checking it against the real screen periodically regardless of how it is built.

**⚠ The browser suite confirmed 6 real claims in the live workspace, as `Rohit`.** `Max depth option` went 15/27 → 21/27 reviewed. Nothing was fabricated or deleted, but real claims were marked confirmed with no person deciding — and it is irreversible by design. The suite drives a shared mutable event log and needs its own workspace before it runs against live data again. It also means the pre-existing "19/19 browser tests" figure was being produced by a suite that mutates the thing it measures.

**The landing page then got a visual identity, scoped so it stops at the sign-in wall.** Its substance was already right; what it was wearing was the *app's* chrome, which is correct for a screen a PM sits in for twenty minutes and wrong for a page a stranger gives eight seconds. `.landing` now declares a magenta → violet → **`--accent`** ramp — the third stop is the product's real interaction blue, so the marketing gesture resolves into the app's palette instead of promising different software. `--accent` itself is untouched and no in-product screen changed; this is a deliberate partial early landing of the deferred `brandkit` accent, and the swap when brandkit lands is two hex values. Also new: a **loop diagram** (`components/landing/loop.tsx`, ring + four cards on one radius, linearises under 900px) and the three acts reworded as the questions a PM actually arrives with. Two honesty constraints bit and are recorded in `docs/decisions/2026-08-16-landing-brand-identity-and-loop-diagram.md`: the customer-logo slot holds *sources* with four of six labelled "not built yet", and the loop's fourth node is "Hand off" rather than the spec assembly that would have closed the circle more neatly and been Phase 2 vapour.

**Then the app chrome caught up with the front door.** Three surfaces, recorded in `docs/decisions/2026-08-16-app-chrome-signin-rail-and-boot.md`. **Sign-in** is now a brand panel beside a form column — the panel still carries the three promises, because the moment before someone hands over a source credential is the moment to state them; no OAuth row and no logo wall, since Atlas has neither. **The rail** is grouped by the loop the product runs (Overview · CONNECT → Sources · REVIEW → Conflicts · FEATURES → the list), with a ⌘K-focusable *filter* (not the v1.x command palette, which is still deferred) and a "Work left" block reading `ScopeCounts` off the projection, so the rail can never disagree with the screen it opens. There is deliberately **no third "Extract" group** — extraction is triggered from Sources and has no screen, and a nav heading over nothing is a promise of a screen that doesn't exist. **Boot** was a blank `<div>` during the session check and is now the Atlas mark in a travelling-arc ring.

**The brand ramp moved from `.landing` to `:root`, and the discipline moved with it, written into the token block:** brand is *chrome only* — mark, rail labels, selected rule, sign-in, boot — and never encodes a claim, status, confidence pip or conflict. That was tested immediately: the rail's new "Work left" meter reports *reviewed*, which is a status fact, so it is painted `--status-confirmed` and not the ramp.

**⚠ The suite's env fallback wasted a 10-minute run and looked like 20 page defects.** With `ATLAS_TEST_EDITOR` / `ATLAS_APP_PASSPHRASE` unset, `ui-smoke.spec.ts` silently falls back to the *local seed's* actors (`Priya (PM)` / `letmein`) and runs them against whatever database `.env` points at. Every sign-in-dependent test failed on an unseated name. Re-run with `ATLAS_TEST_EDITOR="Rohit" ATLAS_TEST_VIEWER="Viewer (demo)"` and the passphrase from `.env`: **25/25 pass** (the two mutating tests excluded, per the warning above; nothing was confirmed). The fallback should fail loudly rather than guess.
