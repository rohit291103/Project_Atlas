## Last session notes

**The database went live, and the security control that was supposed to be waiting there turned out not to work.** No new features. Full write-up: `docs/decisions/2026-08-13-rls-applied-least-privilege-role.md`.

**`FORCE ROW LEVEL SECURITY` was inert, and only a live Postgres could have shown that.** The policy was on, both catalog flags were true, and a connection scoped to workspace A still read workspace B's rows and could still insert into B. The cause is that Supabase's default `postgres` role carries `rolbypassrls`, which **outranks `FORCE`** — `FORCE` only closes the narrower loophole where a table's owner is exempt from its own policies. Slice 1D's reasoning was the right shape and wrong by one level: it correctly saw that the app connects as the table owner, and reached for the wrong lever. This is the failure mode the whole project is most exposed to — a guarantee that is documented, tested, reviewed, and false.

**The fix was a different role, not a different policy.** `atlas_app` is `NOSUPERUSER NOBYPASSRLS` and holds `SELECT`+`INSERT` on `event_log` and `SELECT` on the workspace tables — nothing else. The absent `UPDATE`/`DELETE` is the part worth keeping: **the append-only event log is now enforced by Postgres rather than by the application choosing to behave.** Credentials split into an admin URL (Alembic only) and the app URL. Confirmed the hard way — cleaning up my own probe rows required the admin URL, because the app role genuinely cannot delete.

**A third defect: fail-closed was failing loudly.** With the policy finally binding, an unscoped query raised `invalid input syntax for type uuid: ""` instead of returning nothing. Through a pooler, a *reset* custom GUC holds `''` rather than being absent, and `''::uuid` raises where `NULL` would have filtered. Whether you got a 500 or zero rows depended on whether the recycled backend had been scoped before — `nullif(..., '')` makes it deterministic.

**The "paused Supabase project" from last session was a misdiagnosis.** `db.<ref>.supabase.co` publishes an **AAAA record only**, and this machine has a global IPv6 address with no working IPv6 route — so the name resolved to something unreachable, which looks identical to a dead host. The project was up the whole time. The pooler host is the IPv4 path, now recorded in `.env.example`.

**The stack now runs against live Postgres end to end.** All 4 golden PRs re-ingested (60 events), API sign-in, scope list, scope detail with intact provenance URLs and verbatim excerpts, and a confirm write that replayed to `confirmed`. One node in `Max depth option` is confirmed by "Rohit" as a result of that test — a real event in an append-only log, left in place rather than quietly deleted.

**Then Jira went live, and the same pattern repeated: the first real run found a Critical defect that no fixture could have.** `GET /rest/api/3/search/jql` returns **only issue ids** unless `fields` is named — a 200, not an error. Those field-less objects parsed into issues with an empty key and a provenance URL of `<site>/browse/`, a link resolving to a page with nothing to do with the claim. A 405 further downstream is the only reason the run failed loudly instead of storing four nodes with plausible, wrong provenance. That is precisely the failure this product exists to prevent, and the fixtures could never have caught it because they record the endpoint's *documented* shape. Fixed, plus a guard rejecting any issue with no key, both regression-tested.

**With that fixed, the cross-source thesis is demonstrated on real data for the first time.** An epic and four tickets ingested into the existing `Max depth option` scope: 27 nodes (8 GitHub, 17 Jira), every excerpt verbatim, and **5 cross-source conflicts at 0.9 confidence — all genuine disagreements**. The best of them connects a Jira product decision ("`--maxdepth 0` must still return matches inside the current directory") to GNU-find evidence quoted from a man page inside a code review, across two tools, in the right direction. The review page shows one card carrying a GitHub requirement with two contradicting Jira decisions stacked above its own excerpt — the thing neither tool could have shown alone.

**The seed tickets were written by a scratchpad script, not through `ingestion/jira.py`.** Atlas is read-only into every source system in every scoped phase; a fixture generator is not allowed to be the exception that puts a write path into the module.

**Deliberately not done:** Jira extraction *quality* has no golden set or rubric — one run on four tickets written to be extractable is not evidence of quality; the `frontend-reviewer` pass; nothing committed.
